# Серверная версия «Мастерской» — экспериментальная ветка

**Статус:** серверная основа подготовлена, но **не развёрнута**. Действующий сайт GitHub Pages продолжает работать локально, без связи с этой базой. Код ветки не следует считать прошедшим полный аудит безопасности или проверку с реальными данными.

## Состав

- Node.js: один HTTP-сервер приложения, закрытые API и защищённые сессии.
- PostgreSQL 16: пользователь, текущая JSON-база, ревизия, резервные версии (до 30 предыдущих снимков).
- Docker Compose: приложение, БД и ежедневный `pg_dump` в отдельном томе (30 дней).
- Отдельный клиент `sync-client.js`: вход, ручной выбор исходной базы, явная отправка или получение данных. После выбора — отправка последующих локальных сохранений с проверкой ревизии.

**Это один аккаунт владельца**, а не готовая многопользовательская подписная платформа. Нет восстановления пароля по почте, управления ролями, оплаты и серверной аналитики.

## Перед развёртыванием

Нужны Ubuntu/Docker Compose, доступный поддомен (например, `masterskaya.example.ru`) и **HTTPS через отдельный обратный прокси**. Контейнер приложения слушает только `127.0.0.1:3100`, а PostgreSQL не публикуется в сеть.

Содержимое каталога `server/` должно оставаться внутри репозитория при сборке: конфигурация `server/compose.yaml` ссылается на корень как контекст. Это **не инструкция запускать сервер на GitHub Pages**.

1. На сервере клонируйте рабочую ветку `feature/server-sync-foundation`; не переключайте рабочий GitHub Pages.
2. Создайте `server/.env` на основе `server/.env.example`. `APP_ORIGIN` — **точный** HTTPS-адрес нового домена, без косой черты в конце. Пароль БД и `SETUP_TOKEN` создайте независимо друг от друга из криптографически случайных значений длиной не менее 32 символов.
3. Настройте HTTPS-прокси с перенаправлением запросов на `http://127.0.0.1:3100`. Перед запуском проверьте, что сертификат и домен действуют, порт 3100 извне недоступен. Запросы API должны оставаться на том же домене, что и приложение.
4. Из корня репозитория выполните:
   ```sh
   docker compose --env-file server/.env -f server/compose.yaml up -d --build
   docker compose --env-file server/.env -f server/compose.yaml ps
   curl -fsS http://127.0.0.1:3100/health
   ```
5. Зайдите на новый HTTPS-адрес и создайте первый аккаунт, используя установочный код. В дальнейшем входите по почте и паролю. Установочный код не добавляйте в историю команд, логи и репозиторий.

**Не объединяйте каталог данных этого экспериментального сервера с другими проектами:** для него предусмотрена собственная база и собственные Docker-тома.

## Безопасный перенос старых данных

1. В текущей «Мастерской» на GitHub Pages откройте **«Настройки» → экспорт JSON**. Сохраните файл вне браузера и сделайте вторую копию. Проверьте, что файл не пустой.
2. На новом серверном домене войдите в созданный аккаунт. Локальное хранилище другого домена изначально пустое.
3. Через **«Настройки» → импорт JSON** загрузите сохранённый файл на **новом домене**. Проверьте материалы, закупки и остатки.
4. Откройте **«Синхронизация» → «Отправить локальную базу»**. Проверьте предупреждение о замене удалённых данных. Первое сохранение создаст серверную ревизию.
5. На втором устройстве зайдите на тот же **серверный домен** и в аккаунт, затем нажмите **«Открыть серверную базу»**. Не создавайте параллельно независимые базы.

При работе на другом устройстве оставляйте первый браузер закрытым или не делайте параллельные изменения. Если сервер сообщает о конфликте ревизий, **сначала экспортируйте локальную JSON-копию**. Затем сравните состояния и вручную выберите правильное; автоматического слияния изменений пока нет. Пока не выполнено тестирование, всегда сохраняйте ежедневные JSON-копии.

## Резервные копии и восстановление

- Сервер сохраняет до **30 предыдущих ревизий** в `ms_backups`. Список доступен через `GET /api/backups`, отдельная запись — через `GET /api/backups/:id` после входа. Автоматического восстановления из UI пока нет: сначала скачайте нужный JSON и импортируйте его локально, затем вручную отправьте в сервер.
- Фоновый контейнер `backup` делает дамп БД `pg_dump -Fc` один раз за 24 часа в том `backups_data`. Это локальный том Docker, **не внешняя резервная копия**. Переносите дампы на независимое защищённое хранилище.
- Для проверки дампа и восстановления нужен отдельный тестовый экземпляр PostgreSQL. Не выполняйте `pg_restore --clean` на рабочей базе без проверенного плана восстановления.
- Сохраняйте отдельно `server/.env` в защищённом менеджере секретов; никогда не включайте его в Git.
- Следите за размером БД и тома резервных копий. Для состояния приложения установлен лимит 5 МБ.

## Что ещё требуется до настоящего запуска

1. Выполнить `npm install`, `npm test`, пробный запуск Docker Compose с PostgreSQL и проверить вход/выход и независимые сессии.
2. Провести браузерный регрессионный тест на телефоне и компьютере: перенос старого JSON, закупки, ФИФО, производство, продажи, инвентаризация, переавторизация, потеря сети и конфликты.
3. Добавить мониторинг доступности, проверку дампов восстановлением, автоматическую выгрузку бэкапов за пределы сервера.
4. Провести проверку безопасности перед размещением реальной финансовой и операционной информации.
5. Только после этого перенаправлять пользователей на собственный домен. Старую версию сохраняйте как резервную до подтверждённой миграции.
